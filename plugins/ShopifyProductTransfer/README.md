# Shopify Product Transfer

Import UTF-8 Shopify product CSV files and export selected or all LONGOS products as Shopify-compatible CSV files.

When the plugin is installed or enabled from the admin panel, its pending database migration runs automatically. No Artisan command is required. The migration stores the original Shopify Handle, so later imports can update the same product safely. Products with a matching SKU are also detected.

Product images (`Image Src`), variant images, and images embedded in `Body (HTML)` are downloaded during import into the current tenant's isolated `upload/shopify-products` directory. Every download is restricted to public HTTP/HTTPS hosts, pinned to the validated DNS address, capped by the configured size limit, and verified by real MIME type and image dimensions. Failed downloads are omitted and reported as image warnings; external image URLs are not retained in the imported product. Replacing a product removes only superseded files owned by this plugin.

The importer supports the core Shopify product columns including product information, up to three options, variants, prices, inventory, product status, vendor, type/category, SEO fields and image URLs. LONGOS currently has no native product tag field, barcode field, or Shopify inventory-location model, so those fields are accepted but not persisted.

Version 1.2 adds tenant-isolated local image storage, product/variant/description image localization, safe cleanup of superseded plugin-owned files, and visible image-download warnings. It also includes header-aware comma/semicolon/tab detection, duplicate-header validation, stable Unicode handles, bounded images and inventory, stale Handle recovery, transaction-safe Handle updates, stricter imported HTML sanitization, and spreadsheet-formula protection on export. A failed product does not roll back products that were imported successfully before it; the result summary lists up to 100 actionable product errors.

Version 1.3 fixes the completed-import 500 caused by array-valued translation replacements, always redirects submissions back to the plugin page, recovers safe GET requests to the import URL, detects the effective PHP upload limit in both the browser and controller, and reports oversized POST requests without exposing the generic error page. Remote image downloads now finish before the short database write transaction, preventing slow Shopify CDN responses from holding tenant locks open. Import/export round trips and local tenant image persistence remain covered by automated tests.

Version 1.4 indexes large CSV files by byte offset and re-reads only one product at a time, avoiding the previous full-file row array in PHP memory. Replacement imports now persist the new product gallery before stale files are deleted. Shopify category hierarchies create complete LONGOS category paths, invalidate catalog caches correctly, and round-trip back to Shopify CSV. Duplicate option combinations, invalid numeric values, oversized products, and unsafe duplicate image sources fail closed instead of silently losing data. The admin page also exposes a standard CSV template download and preserves failed form choices.

Version 1.6 accepts both Shopify's current product CSV names (`URL handle`, `Description`, `SKU`, `Barcodes`, `Option1 LinkedTo`, `Product image URL`, and related fields) and legacy names retained by older exports. Templates and exports emit the current core column set, including packed-product dimensions, and preserve multi-variant round trips. Plugin routes also follow LONGOS product permissions: viewing/export requires product-list access, importing requires product-create access, and replacement imports additionally require product-update access. On production queue connections, uploaded CSV files move to private storage and import in a tenant-aware background job with persisted progress, cleanup, and a synchronous fallback when queue infrastructure is unavailable. This prevents large image imports from holding one browser request open until a proxy timeout. If a release package is copied before its normal upgrade pass runs, the plugin page safely applies its own idempotent support-table migrations; a database permission problem is shown as an actionable admin message instead of a generic 500 page.

Version 1.6.3 makes replacement imports fail closed when any referenced remote image cannot be downloaded. The existing product, gallery, variants, description, and plugin-owned files remain unchanged, and any partial new downloads are removed, so a temporary Shopify/CDN failure cannot silently damage a live product. Background runs also use an atomic pending-to-running lease: duplicate queue delivery cannot import the same CSV twice or delete the private upload while its owning worker is still using it.

Version 1.6.4 detects whether a worker for this exact LONGOS project and queue is actually running instead of assuming that a configured database queue is healthy. When no worker is available, the admin page automatically and securely processes its own pending import through a CSRF-protected tenant-scoped endpoint; a visible Process now fallback remains available if browser automation is interrupted. Existing tasks stuck at Waiting are recovered without requiring a server command.

Version 1.6.5 adds a shared-storage worker heartbeat, so the web container correctly sees the separate LONGOS worker container. If no worker exists, a tenant-captured after-response fallback starts automatically after the upload redirect has been sent, avoiding both a permanently waiting job and a long upload response that can be cut off by a reverse-proxy timeout. The page recovery endpoint remains as a crash-safe fallback.

Version 1.6.6 makes page-triggered recovery genuinely non-blocking: the HTTP response is returned first and tenant-captured import work continues afterward, so a proxy timeout or closed browser does not cancel the task. Recovery leases are now calculated from both the job timeout and the configured queue reservation instead of using an unsafe fixed duration. Per-worker shared-storage heartbeats keep busy Docker workers visible without one worker clearing another worker's lease. Transient image downloads are retried once, database SKU matching is case-insensitive on MySQL, PostgreSQL, and SQLite, and opened CSV streams are closed on every validation or runtime failure.

Version 1.6.7 accepts real Shopify exports in which one merchant SKU is reused by multiple products or variants. Shopify Handle is now the authoritative product identity; SKU is only a safe fallback for an unmapped legacy LONGOS product. Because LONGOS uses a globally unique, 32-character SKU as its cart and stock key, repeated or longer source values receive deterministic compatible internal SKUs while a tenant-isolated mapping preserves the exact Shopify SKU on export. Replacement imports keep targeting the correct Handle and cannot overwrite another product merely because the source store reused its SKU. Current Shopify `unlisted` status, negative oversold inventory, and Vendor-driven brand creation are also imported safely.

An import left in Running by a terminated worker becomes recoverable only after its calculated execution lease expires. Recovery atomically resets stale progress and reprocesses the retained private CSV; a duplicate live worker cannot acquire that lease.

Version 1.6.1 fixes the admin-page Blade compilation failure caused by a nested `@json` expression under the production compiler. Runtime upload-limit text is now prepared by the controller and the compiled template is syntax-checked by a regression test. Startup readiness also repairs legacy partial import tables, verifies every column used by the queue/status UI, and safely handles incomplete historical task records without passing null paths to storage cleanup.

Version 1.6.2 isolates import-history failures from the page response, removes expired private CSV files before their database records, and restricts all task cleanup to UUID-named files inside the private `shopify-imports` directory. Invalid legacy paths fail safely without touching unrelated storage. The unavailable-schema state now remains disabled after browser back/forward restoration, and every plugin Blade template is syntax-parsed in the automated suite.
